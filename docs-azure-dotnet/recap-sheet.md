# Azure recap sheet

Use this sheet for revision after the lessons or as a map before them.

Verified as of 2026-10-17.

Service availability depends on region, model, plan and subscription; check them together before choosing a deployment. [Preview features carry no SLA](https://azure.microsoft.com/en-in/support/legal/faq) and [are not recommended for production](https://learn.microsoft.com/en-us/lifecycle/faq/azure-infrastructure).

## 1. Mental model in ten lines \{#mental-model}

1. Microsoft Entra tenant → management groups → subscriptions → resource groups → resources is the identity and governance map; the tenant is an identity directory, not a deployed network.
2. [Microsoft Entra ID](https://learn.microsoft.com/en-us/entra/fundamentals/new-name) authenticates people and workloads; formerly Azure Active Directory (Azure AD).
3. [Management groups](https://learn.microsoft.com/en-us/azure/governance/management-groups/overview) collect subscriptions so organization-wide Azure Policy and RBAC assignments can flow down the hierarchy.
4. Subscriptions separate resource administration, quotas and accumulated charges; [billing accounts](https://learn.microsoft.com/en-us/azure/cost-management-billing/understand/understand-billing-tenant-relationship) handle commercial invoicing under a separate billing hierarchy.
5. Resource groups collect resources with a shared lifecycle; deleting a group deletes its resources. A group can contain resources in different regions.
6. Resources are managed service instances: a database, network, application or model-hosting account; each has a resource ID and resource-provider type.
7. [Azure Resource Manager (ARM)](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/overview) is the common control plane behind portal, CLI, SDK and IaC management operations; application traffic uses service data planes.
8. Regions locate deployments; choose using latency, residency, service availability and recovery requirements.
9. [Availability zones](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview) separate datacenter infrastructure within a region; zone resilience needs service-specific configuration and does not replace regional disaster recovery.
10. RBAC and Policy attach at management group, subscription, resource group or resource scope and inherit downward; billing scopes and Entra directory roles are separate concepts.

## 2. Identity and access \{#identity-and-access}

| Concept | Problem solved and mechanism |
|---|---|
| Users and groups | Users represent people; groups let administrators grant access to a maintained membership rather than many individual accounts. |
| [App registration](https://learn.microsoft.com/en-us/entra/identity-platform/app-objects-and-service-principals) | Defines an application's identity blueprint: client ID, sign-in settings, exposed APIs and requested permissions. |
| [Service principal](https://learn.microsoft.com/en-us/entra/identity-platform/app-objects-and-service-principals) | The application's local identity in a tenant, to which access is granted; one application can have a service principal in each consuming tenant. |
| [Managed identity](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/overview) | A special service principal whose credentials Azure manages; an attached workload obtains Entra tokens without storing passwords or keys. |
| System-assigned vs user-assigned | System-assigned identity belongs to one resource and dies with it. User-assigned identity is a separate resource, can be attached to multiple workloads, and survives their replacement. |
| [Azure RBAC](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview) | Assignment = principal + role definition + scope. Roles specify allowed operations; inherited grants remain effective—a narrower Reader assignment does not cancel an inherited Contributor grant. |
| [Management vs data access](https://learn.microsoft.com/en-us/azure/storage/blobs/authorize-data-operations-portal) | Owner: manage resources and access; Contributor: manage resources, not assign roles; Reader: inspect resource configuration. Reading actual data typically needs a data role, such as Storage Blob Data Reader or Key Vault Secrets User; management privilege can still allow indirect access or granting access. |
| [Workload identity federation](https://learn.microsoft.com/en-us/azure/developer/github/connect-from-azure-openid-connect) | GitHub Actions receives a short-lived OIDC token; Entra validates issuer, subject and audience against a federated credential on an app or user-assigned identity, then issues an Azure access token. Use `id-token: write`, narrowly scoped RBAC and a trusted branch or environment; no stored client secret. |
| [Conditional Access](https://learn.microsoft.com/en-us/entra/identity/conditional-access/overview) | Identity policies evaluate signals such as user, device, location and risk, then require controls such as MFA or block access. |
| [Keyless SDK access](https://learn.microsoft.com/en-us/dotnet/api/azure.identity.defaultazurecredential?view=azure-dotnet) | `DefaultAzureCredential` tries configured credential sources: developer login locally, managed identity in Azure when configured. Pass the credential to SDK clients; explicitly select and constrain the production credential—often `ManagedIdentityCredential`—and grant the target service's data role. |

Separate three checks: can the client reach the endpoint, obtain the right token, and perform the requested operation?

## 3. Networking \{#networking}

| Building block | What it does and when it matters |
|---|---|
| [VNet; subnet](https://learn.microsoft.com/en-us/azure/security/fundamentals/network-overview) | A Virtual Network supplies isolated private IP space and routing. Subnets divide that address space for workloads, service integration and network controls. |
| Network security group (NSG) | Stateful allow or deny packet rules on subnets or network interfaces, based on addresses, ports and protocols; useful for restricting traffic between application tiers. |
| [Private endpoint](https://learn.microsoft.com/en-us/azure/virtual-network/vnet-integration-for-azure-services) | A network interface with a private IP in your VNet exposes a supported service through Azure Private Link. Configure public access separately; creating the endpoint alone is not a complete isolation design. |
| [Service endpoint](https://learn.microsoft.com/en-us/azure/virtual-network/vnet-integration-for-azure-services) | Identifies an allowed subnet to a supported service while accessing its public endpoint over the Azure backbone; it does not create a private IP for that service. |
| Private DNS zone | Supplies private name resolution to linked VNets so normal service hostnames resolve to private endpoint addresses. Custom or on-premises DNS needs suitable forwarding. |
| [PaaS VNet integration](https://learn.microsoft.com/en-us/azure/app-service/overview-vnet-integration) | Gives a hosted app an outbound route into a VNet to reach private dependencies. For App Service, inbound private access uses a private endpoint separately. |
| [Hub-and-spoke; Azure Firewall](https://learn.microsoft.com/en-us/azure/architecture/networking/architecture/hub-spoke) | Workload VNets connect to a shared hub for connectivity, DNS and inspection. Azure Firewall centrally filters and logs routed traffic; [VNet peering is nontransitive](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-networks-faq), so spoke-to-spoke inspection needs deliberate routes. |
| [Application Gateway + WAF](https://learn.microsoft.com/en-us/azure/networking/design-guide/app-delivery) | Regional HTTP(S) reverse proxy: TLS termination, host and path routing and Web Application Firewall inspection near regional backends. |
| [Azure Front Door + WAF](https://learn.microsoft.com/en-us/azure/networking/design-guide/app-delivery) | Global HTTP(S) edge entry point: route to healthy regional backends, accelerate and cache content and apply WAF rules. |
| [Azure Load Balancer](https://learn.microsoft.com/en-us/azure/networking/design-guide/app-delivery) | Distributes TCP and UDP flows using health probes; choose for transport-level balancing without HTTP path routing or WAF inspection. |

## 4. Compute decision table \{#compute}

| Service | Use for | Scaling and operations | Avoid when |
|---|---|---|---|
| [App Service](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling) | Web apps and APIs deployed as code or containers | Managed hosting on an App Service plan; scale instances manually or by supported autoscale or automatic-scaling options | Kubernetes APIs or specialized infrastructure control are required |
| [Azure Container Apps](https://learn.microsoft.com/en-us/azure/container-apps/scale-app) | Containerized APIs, workers and jobs | Managed environment; KEDA drives replica autoscaling from HTTP traffic, events or metrics, including scale-to-zero where configured; no Kubernetes API to operate | You need cluster-level control; keep minimum replicas if cold starts violate latency goals |
| [Azure Functions — Flex Consumption](https://learn.microsoft.com/en-us/azure/azure-functions/flex-consumption-plan) | Triggered processing and small event-driven endpoints | Linux serverless plan; per-function scaling with some trigger groups, scale-to-zero, optional paid always-ready instances; supports VNet integration | You need a continuously running custom server or OS control; assess long HTTP requests and cold starts |
| [Azure Kubernetes Service (AKS)](https://learn.microsoft.com/en-us/azure/architecture/guide/technology-choices/compute-decision-tree) | Workloads needing Kubernetes APIs, ecosystem and orchestration control | Managed control plane; you operate workload and node configuration, upgrades and policies; pod and node scaling are separate | A small API or worker can use managed application hosting; cluster operations add responsibility |
| [Virtual Machines (VMs)](https://learn.microsoft.com/en-us/azure/architecture/guide/technology-choices/compute-decision-tree) | OS-specific software, legacy applications, full machine control | You maintain OS and software; VM Scale Sets add or remove machines | A managed runtime or database meets the requirement and removes patching work |

## 5. Data \{#data}

| Service | When and how |
|---|---|
| [Blob Storage](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-overview) | Object storage for files, documents and ingestion artifacts. Hot, Cool and Cold trade storage price against access charges; Archive is offline and must be rehydrated before reading; [Smart](https://learn.microsoft.com/en-us/azure/storage/blobs/access-tiers-smart) (GA in public cloud regions with zonal redundancy; Standard GPv2 accounts using ZRS, GZRS or RA-GZRS; block blobs) moves objects hot → cool after 30 idle days → cold after 90, back to hot on access. |
| [Azure SQL Database](https://learn.microsoft.com/en-us/azure/azure-sql/database/sql-database-paas-overview?view=azuresql) | Managed SQL Server-engine relational database when transactions, joins and T-SQL fit; Microsoft handles infrastructure patching and backups, while schema and query design remain yours. |
| [Azure Database for PostgreSQL flexible server](https://learn.microsoft.com/en-us/azure/postgresql/extensions/how-to-use-pgvector) | Managed PostgreSQL when its SQL features and ecosystem fit; pgvector stores and searches embeddings alongside relational data. Allowlist `vector`, then run `CREATE EXTENSION vector` in the database. |
| [Azure Cosmos DB for NoSQL](https://learn.microsoft.com/en-us/azure/cosmos-db/request-units) | Partitioned document database for distributed access and scale; partition-key choice controls data distribution. Request units (RUs) measure operation cost; provision throughput in RU/s or choose an appropriate consumption model. [Vector search](https://learn.microsoft.com/en-us/azure/cosmos-db/vector-search) indexes embeddings beside documents. |
| [Azure Managed Redis](https://learn.microsoft.com/en-us/azure/redis/overview) | Managed in-memory store for caches, sessions and other latency-sensitive access; define TTL, eviction and cache invalidation rules rather than treating cached data as automatically current. |

[Cosmos consistency](https://learn.microsoft.com/en-us/azure/cosmos-db/consistency-levels), strongest → weakest: Strong = latest committed state; Bounded staleness = bounded lag; Session = guarantees such as read-your-writes within a session; Consistent prefix = ordered writes without gaps; Eventual = convergence without a freshness or ordering guarantee. Stronger guarantees trade against latency, availability and throughput.

## 6. Messaging — Service Bus vs Event Grid vs Event Hubs \{#messaging}

| Service | Contract and mechanism | Typical choice | Delivery design |
|---|---|---|---|
| [Service Bus](https://learn.microsoft.com/en-us/azure/service-bus-messaging/compare-messaging-services) | Brokered queues and topic subscriptions; consumers complete work and acknowledge messages | Commands and workflows where processing matters; dead-lettering. Basic lacks [transactions](https://learn.microsoft.com/en-us/azure/service-bus-messaging/service-bus-transactions) and [sessions](https://learn.microsoft.com/en-us/azure/service-bus-messaging/message-sessions); Standard and Premium include both, with sessions enabling ordered processing | Handle redelivery; [duplicate detection](https://learn.microsoft.com/en-us/azure/architecture/guide/technology-choices/messaging) does not make external side effects exactly-once |
| [Event Grid](https://learn.microsoft.com/en-us/azure/service-bus-messaging/compare-messaging-services) | Routes discrete events to interested subscribers | “A blob was created”; react to state changes without coupling publisher to handler | Expect duplicates and no general ordering guarantee |
| [Event Hubs](https://learn.microsoft.com/en-us/azure/service-bus-messaging/compare-messaging-services) | Partitioned append stream; consumer groups track positions independently | Telemetry and high-volume ingestion; retained events support replay | Order is per partition; consumers manage checkpoints and idempotency |

Selection question: is this work that must complete, a notification, or a stream to analyze?

## 7. Secrets and config \{#secrets-and-config}

- [Key Vault](https://learn.microsoft.com/en-us/azure/key-vault/general/apps-api-keys-secrets): secrets hold sensitive values; keys support cryptographic operations; certificates support certificate lifecycle management. Use the [Azure RBAC permission model](https://learn.microsoft.com/en-us/azure/key-vault/general/rbac-guide) with separate management and data permissions and least-privilege roles, rather than designing around legacy access policies.
- [App Configuration](https://learn.microsoft.com/en-us/azure/azure-app-configuration/overview): central key-value settings and feature flags decouple configuration changes from application binaries; sensitive values belong in Key Vault, with references where appropriate.
- Access path: enable the application's managed identity; assign Key Vault Secrets User and [App Configuration Data Reader](https://learn.microsoft.com/en-us/azure/azure-app-configuration/concept-enable-rbac) where needed; use token-authenticated clients and providers. Identity grants do not create network connectivity.

## 8. Infrastructure as code and delivery \{#infrastructure-and-delivery}

For the release method, see [observability and rollout](/ai-sdlc/part-4-platform/observability-rollout); the table maps it to Azure mechanisms.

| Tool or mechanism | Purpose and distinction |
|---|---|
| [ARM vs Bicep](https://learn.microsoft.com/en-us/azure/developer/terraform/comparing-terraform-and-bicep) | ARM is the control plane; an ARM template is its declarative JSON deployment format. Bicep is a concise Azure-specific language compiled to that format; no separate client-managed state file. |
| [Terraform](https://learn.microsoft.com/en-us/azure/developer/terraform/comparing-terraform-and-bicep) | Declarative infrastructure using providers across Azure and other platforms; plans changes using stored state. Secure the shared state and backend and review changes before applying. |
| [Azure Developer CLI (`azd`)](https://learn.microsoft.com/en-us/azure/developer/azure-developer-cli/overview) | Packages repeatable application provisioning and deployment workflows around code and IaC; `azd up` provisions and deploys. It orchestrates the workflow rather than replacing Bicep or Terraform. |
| [GitHub Actions](https://docs.github.com/en/actions/get-started/understand-github-actions) vs [Azure Pipelines](https://learn.microsoft.com/en-us/azure/devops/pipelines/get-started/what-is-azure-pipelines?view=azure-devops) | Both execute CI/CD jobs: build, test, provision and deploy. Actions integrates with GitHub workflows; Azure Pipelines is the pipeline service in Azure DevOps; choose with the team's repository, runner and governance setup. |
| [App Service deployment slots](https://learn.microsoft.com/en-us/azure/app-service/deploy-staging-slots) | Deploy to a staging app endpoint, validate, then swap into production; [available on Standard, Premium and Isolated plans](https://learn.microsoft.com/en-us/azure/app-service/deploy-staging-slots). Keep slot-specific settings deliberate and database changes compatible with rollback. |
| [Container Apps revisions](https://learn.microsoft.com/en-us/azure/container-apps/revisions) | Versioned application snapshots; multiple active revisions permit traffic splitting, staged rollout and rollback. App-wide configuration changes are not all revision-scoped. |

Delivery sequence: review IaC → tests → build immutable image → OIDC login → provision and deploy → readiness and smoke checks → shift traffic → monitor and roll back if needed.

## 9. Observability \{#observability}

- [Azure Monitor](https://learn.microsoft.com/en-us/azure/azure-monitor/fundamentals/overview): collects and acts on infrastructure and application telemetry; metrics and logs support dashboards and alerts.
- Log Analytics workspace: stores log and trace tables and controls query access; Application Insights adds application performance views, dependencies, failures and distributed tracing.
- OpenTelemetry: instruments traces, metrics and logs independently of a backend. [Current .NET, Node.js and Python guidance](https://learn.microsoft.com/en-us/azure/azure-monitor/app/opentelemetry-enable) recommends Microsoft OpenTelemetry Distro; existing Azure Monitor OpenTelemetry Distro integrations can remain in place, and Java uses that distro. Export to Azure Monitor; correlate requests, model calls and retrieval spans.
- KQL (Kusto Query Language): pipe tables through filters and aggregations. These queries use the [AppRequests](https://learn.microsoft.com/en-us/azure/azure-monitor/reference/tables/apprequests) and [AppExceptions](https://learn.microsoft.com/en-us/azure/azure-monitor/reference/tables/appexceptions) workspace table names and assume telemetry is arriving; they were checked against the documented schemas; they have not been run against live Azure. Counts are stored records, and the [p95 is an estimate](https://learn.microsoft.com/en-us/kusto/query/percentiles-aggregation-function?view=azure-data-explorer) over those records; sampling can change both totals and the observed latency distribution.

```kusto
// Failed request records during the last hour
AppRequests | where TimeGenerated > ago(1h) and Success == false
| summarize Failures=count() by bin(TimeGenerated, 5m)
```

```kusto
// Slow endpoints: p95 duration in milliseconds
AppRequests | where TimeGenerated > ago(1h)
| summarize P95=percentile(DurationMs, 95) by Name | top 5 by P95 desc
```

```kusto
// Most frequent exception groups
AppExceptions | where TimeGenerated > ago(1h)
| summarize Records=count() by ProblemId | top 5 by Records desc
```

## 11. AI on Azure \{#ai-on-azure}

The underlying methods are covered in [retrieval](/rag-agents/part-1-rag/retrieval/), [tool use](/rag-agents/part-2-agents/tool-use/) and [evaluation](/rag-agents/part-1-rag/cross-cutting/evaluation/).

[Microsoft Foundry](https://learn.microsoft.com/en-us/azure/foundry/what-is-foundry) is the current name for Azure AI Foundry. A [Foundry resource](https://learn.microsoft.com/en-us/azure/foundry/concepts/architecture) owns shared networking, security and model deployments; projects organize agents, evaluations and development assets inside it. Connected Search, Storage and Key Vault resources retain their own access and network boundaries; older hub-based projects belong to the classic experience.

A [model deployment](https://learn.microsoft.com/en-us/azure/foundry-classic/openai/how-to/create-resource) is a named endpoint for one model version with a chosen deployment type and capacity; code calls the deployment name. Azure OpenAI in Microsoft Foundry Models supplies OpenAI models; the catalog also includes other providers—check each model's API, deployment options and terms rather than assuming identical behavior.

The table covers the main online [Serverless API deployment types](https://learn.microsoft.com/en-us/azure/foundry/concepts/deployments-overview); managed compute has a separate deployment model. [Processing boundaries and billing](https://learn.microsoft.com/en-us/azure/foundry/foundry-models/concepts/deployment-types) depend on the selected type.

| Deployment choice | Processing, latency and cost |
|---|---|
| [Standard](https://learn.microsoft.com/en-us/azure/foundry/foundry-models/concepts/deployment-types) | Pay per token; processing within the selected Azure geography, potentially across its regions. Variable latency and throughput; validate availability for the model and deployment type. |
| [Global Standard](https://learn.microsoft.com/en-us/azure/foundry/foundry-models/concepts/deployment-types) | Pay per token; requests may be processed across Azure regions globally to use available capacity. Global routing is not a promise of low or fixed latency. |
| [Data Zone Standard](https://learn.microsoft.com/en-us/azure/foundry/foundry-models/concepts/deployment-types) | Pay per token; processing stays within Microsoft's specified US, EU or APAC data zone, potentially spanning regions; standard latency can vary. |
| [Provisioned (PTU)](https://learn.microsoft.com/en-us/azure/foundry/foundry-models/concepts/deployment-types) | Reserve processing capacity in provisioned throughput units for predictable throughput and lower latency variation; pay for capacity, including idle capacity. Global Provisioned, Data Zone Provisioned, Regional Provisioned supply the corresponding processing boundaries. |

Residency: [stored-at-rest location and inference-processing location are separate decisions](https://learn.microsoft.com/en-us/azure/foundry/foundry-models/concepts/deployment-types). Size PTUs using the actual model and token workload.

| Capability | What it solves and how it affects design |
|---|---|
| [Quotas: TPM and RPM](https://learn.microsoft.com/en-us/azure/foundry/openai/quotas-limits) | Tokens per minute and requests per minute constrain traffic; allocation depends on subscription, model, region and deployment type. Check the model-specific ratio; bound concurrency, handle 429 responses and `Retry-After`, and request increases rather than memorizing a universal limit. |
| [Content filtering; Azure AI Content Safety](https://learn.microsoft.com/en-us/azure/foundry/guardrails/guardrails-overview) | Classifiers detect harmful inputs and outputs; Foundry guardrails use Content Safety models. Configure supported controls and test false positives and false negatives; agent guardrails, including tool-call and tool-response intervention points, are preview. |
| [Prompt Shields](https://learn.microsoft.com/en-us/azure/foundry/openai/concepts/content-filter-prompt-shields) | Detects direct prompt attacks and instructions hidden in document content. [Document-attack detection is off by default and must be enabled](https://learn.microsoft.com/en-us/azure/foundry/openai/concepts/content-filter-prompt-shields); agent tool-response scanning is preview. Supplement with authorization, restricted tools and output validation; detection is not a guarantee against injection. |
| [Azure AI Search](https://learn.microsoft.com/en-us/azure/search/search-relevance-overview) | Managed retrieval indexes text and vectors. Hybrid search runs keyword and vector retrieval and merges rankings using reciprocal rank fusion (RRF); the optional semantic ranker rescores retrieved results for relevance. |
| [Integrated vectorization](https://learn.microsoft.com/en-us/azure/search/vector-search-integrated-vectorization) | Indexer pipelines with skills can chunk and embed source content; query vectorizers embed incoming queries. This reduces pipeline code but still needs ingestion monitoring, model quota and evaluation. |
| [Agentic retrieval](https://learn.microsoft.com/en-us/azure/search/agentic-retrieval-overview) | Knowledge bases coordinate retrieval and return grounding content and references. Minimal, extractive retrieval over GA knowledge-source types has GA support; LLM query planning, non-minimal reasoning, multi-turn input and answer synthesis remain preview—do not label the whole feature uniformly GA or preview. |
| [Content Understanding and Document Intelligence](https://learn.microsoft.com/en-us/azure/ai-services/content-understanding/choosing-right-ai-tool) | For OCR or layout only, use Content Understanding `prebuilt-read` or `prebuilt-layout`. For standard structured forms, use Document Intelligence prebuilt models or labelled custom extraction. For unstructured or multimodal content, or inferred fields, use Content Understanding analyzers; validate on representative inputs. |
| [Foundry Agent Service](https://learn.microsoft.com/en-us/azure/foundry/agents/overview) | Managed execution: prompt agents run from a configured model, instructions and tools; hosted agents run custom agent code as containers with managed endpoints and scaling. The hosting service is separate from the SDK used to author an agent. |
| [Microsoft Agent Framework](https://learn.microsoft.com/en-us/agent-framework/overview/) | Agent and workflow SDKs for .NET, Python and Go; the successor to Semantic Kernel and AutoGen, with tool use, sessions, middleware and explicit orchestration. Core packages are GA in .NET ([`Microsoft.Agents.AI`, stable on NuGet](https://www.nuget.org/packages/Microsoft.Agents.AI/)) and Python ([`agent-framework` v1.0.0+](https://learn.microsoft.com/en-us/azure/machine-learning/prompt-flow/how-to-migrate-prompt-flow-to-agent-framework?view=azureml-api-2)). [Go is preview; the current .NET Foundry quickstart installs `Microsoft.Agents.AI.Foundry` with `--prerelease`](https://learn.microsoft.com/en-us/agent-framework/overview/). |
| [Foundry evaluation and tracing](https://learn.microsoft.com/en-us/azure/foundry/concepts/observability) | Evaluations measure quality and safety against datasets; traces explain model calls, tools, latency and token use. [OpenTelemetry traces flow to connected Application Insights](https://learn.microsoft.com/en-us/azure/foundry/observability/concepts/trace-data); control what prompt content is captured and who can access it. |
| [API Management as AI gateway](https://learn.microsoft.com/en-us/azure/api-management/genai-gateway-capabilities) | Centralize authentication, per-consumer token limits, semantic caching and routing across deployments. Backend pools and circuit breakers support load balancing and failover. [Semantic caching needs an external cache, such as Azure Managed Redis with RediSearch enabled](https://learn.microsoft.com/en-us/azure/api-management/azure-openai-enable-semantic-caching); reuse needs authorization checks, context isolation and invalidation rules. |
| [Private model endpoints](https://learn.microsoft.com/en-us/azure/foundry/how-to/configure-private-link) | Give Foundry a private endpoint, configure DNS and disable public access where required. The application needs outbound VNet connectivity plus Entra permissions; secure Search, Storage and outbound traffic from agents and tools separately. |

## 12. Modern .NET \{#modern-dotnet}

[.NET 10 is the current LTS](https://learn.microsoft.com/en-us/dotnet/core/releases-and-support), [supported through 2028-11-14; .NET 8 and .NET 9 end support 2026-11-10](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core). Modern .NET is cross-platform; .NET Framework is a separate product line, not the current server-development baseline.

| Mechanism | Problem solved and how it works |
|---|---|
| [SDK-style projects; .NET CLI](https://learn.microsoft.com/en-us/dotnet/core/project-sdk/overview) | An SDK-style `.csproj` declares its SDK and target framework, such as [`net10.0`](https://learn.microsoft.com/en-us/dotnet/standard/frameworks); SDK defaults reduce project-file boilerplate. The [`dotnet` CLI](https://learn.microsoft.com/en-us/dotnet/core/tools/) creates, restores, builds, runs, tests and publishes in local and CI workflows. |
| [NuGet](https://learn.microsoft.com/en-us/nuget/consume-packages/package-references-in-project-files) | Versioned packages replace manually copied library references. `PackageReference` entries declare dependencies; restore resolves and supplies them. |
| [ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/?view=aspnetcore-10.0) | Cross-platform web hosting for APIs and web apps. [Minimal APIs](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/minimal-apis?view=aspnetcore-10.0) map routes to handlers; controllers organize endpoints into classes with MVC conventions and features. |
| [Dependency injection (DI)](https://learn.microsoft.com/en-us/dotnet/core/extensions/dependency-injection/service-lifetimes) | The built-in container resolves registered services: transient per resolution, scoped per scope, singleton per container. A singleton must not capture a request-scoped dependency. |

## 13. Power Platform in six lines \{#power-platform}

1. [Power Apps](https://learn.microsoft.com/en-us/power-platform/developer/get-started): low-code application UI over connected data; pro-code APIs and components extend behavior beyond the visual builder.
2. [Power Automate](https://learn.microsoft.com/en-us/power-platform/developer/get-started): cloud and desktop flows automate triggered, scheduled and interactive work across connectors.
3. [Dataverse](https://learn.microsoft.com/en-us/power-apps/maker/data-platform/data-platform-intro): managed business-data platform with tables, relationships, security and APIs; supplies shared data for platform applications.
4. [Copilot Studio](https://learn.microsoft.com/en-us/power-platform/developer/get-started): graphical low-code builder for agents and agent flows that connects knowledge and tools to conversational experiences.
5. [Custom connectors](https://learn.microsoft.com/en-us/connectors/custom-connectors/): wrap REST APIs as reusable actions and triggers for Power Apps, Power Automate and Copilot Studio; an ASP.NET Core API can provide the backend.
6. Pro-code boundary: put custom logic behind authenticated APIs, expose a connector, and retain explicit data permissions and deployment discipline; test the API and connector together, including authorization failures.

## 14. Ten review questions \{#review-questions}

After the course, you should be able to answer these questions and explain the choices in each outline.

| Question | Answer outline |
|---|---|
| 1. How would you organize an Azure estate? | Start with tenant and management groups for common guardrails; subscriptions separate workload and environment administration and spend. Group resources by lifecycle; assign least-privilege access and Policy at deliberate scopes. |
| 2. Why does Contributor still get an access-denied error? | Separate control-plane permission from the target service's data authorization. Identify the calling principal and token audience, then check its data role, scope and network reachability. |
| 3. How would you make a RAG backend private? | App outbound VNet connectivity → private endpoints and DNS for models, Search and secrets; disable public access where appropriate. Use managed identity and data roles. Also document how ingestion jobs, operators and CI reach these resources. |
| 4. Container Apps, App Service, Functions or AKS? | Choose using request or trigger model, container needs, latency and operations ownership. Prefer a managed application host unless Kubernetes control is required; validate scaling and cold-start behavior against the SLO. |
| 5. How do you recover from a regional outage? | Define recovery time and data-loss objectives, then plan regional app capacity, data replication and backups and routing. Zones address failures inside a region; test failover, restore and dependency availability. |
| 6. Which messaging service fits ingestion? | Event Grid announces new content; Service Bus queues work needing completion; Event Hubs ingests ordered partition streams. Design retries, poison-message handling and idempotency at the application boundary. |
| 7. How do you choose data storage for RAG? | Blob for originals; SQL or PostgreSQL for relational state; Search for managed hybrid retrieval; Cosmos for partitioned document access; Redis for caching. Choose from query and update patterns and measured retrieval quality, not from “vector support” alone. |
| 8. Global Standard or Provisioned models? | Resolve processing-residency constraints first, then measure token mix, concurrency and latency. Compare pay-per-token elasticity against reserved PTU utilization; validate quota, capacity and failover assumptions. |
| 9. How do you release and debug safely? | Version IaC and images, authenticate CI through OIDC, validate before shifting slot or revision traffic. Correlate request, retrieval and model traces; gate retrieval and answer quality with repeatable evals and retain a rollback path. |
| 10. How do you govern cost and security? | Policy enforces configuration; RBAC limits access; Defender for Cloud surfaces risks. Track owner and environment tags, analyze spend and configure budget alerts; add token and concurrency limits because budgets alone do not cap consumption. |
