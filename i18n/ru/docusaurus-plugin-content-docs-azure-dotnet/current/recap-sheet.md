# Шпаргалка по Azure

Перед уроками эта страница поможет сориентироваться в Azure, а после — быстро вспомнить нужные механизмы.

Проверено на 17.10.2026.

Доступность служб зависит от региона, модели, плана и подписки. Перед выбором развёртывания проверь это сочетание параметров. На функции в статусе preview [не распространяется SLA](https://azure.microsoft.com/en-in/support/legal/faq); их [не рекомендуют использовать в проде](https://learn.microsoft.com/ru-ru/lifecycle/faq/azure-infrastructure).

## 1. Десять опорных понятий \{#mental-model}

1. Иерархия: тенант (tenant) Microsoft Entra → группы управления (management groups) → подписки (subscriptions) → группы ресурсов (resource groups) → ресурсы. Эта схема описывает удостоверения и правила управления ресурсами. Тенант — каталог удостоверений, а не развёрнутая сеть.
2. [Microsoft Entra ID](https://learn.microsoft.com/ru-ru/entra/fundamentals/new-name) аутентифицирует людей и рабочие нагрузки. Прежнее название — Azure Active Directory (Azure AD).
3. [Группы управления](https://learn.microsoft.com/ru-ru/azure/governance/management-groups/overview) объединяют подписки: общие назначения Azure Policy и Azure RBAC наследуются ниже по иерархии.
4. Подписка разграничивает администрирование ресурсов, квоты и учёт расходов. [Учётные записи для выставления счетов (billing accounts)](https://learn.microsoft.com/ru-ru/azure/cost-management-billing/understand/understand-billing-tenant-relationship) отвечают за коммерческие отношения и счета; у них своя платёжная иерархия.
5. Группа ресурсов объединяет ресурсы с общим жизненным циклом. При удалении группы удаляются все её ресурсы; находиться они могут в разных регионах.
6. Ресурс — экземпляр службы: база данных, сеть, приложение или учётная запись для размещения моделей. У каждого ресурса есть идентификатор и тип поставщика ресурсов.
7. [Azure Resource Manager (ARM)](https://learn.microsoft.com/ru-ru/azure/azure-resource-manager/management/overview) — общая плоскость управления (control plane), через которую портал, CLI, SDK и инструменты IaC управляют ресурсами. Запросы самого приложения идут через плоскости данных (data planes) соответствующих служб.
8. Регион задаёт место развёртывания. При выборе учитывай задержку, требования к размещению данных, доступность служб и восстановление после аварии.
9. [Зоны доступности (availability zones)](https://learn.microsoft.com/ru-ru/azure/reliability/availability-zones-overview) разделяют инфраструктуру центров обработки данных внутри региона. Отказоустойчивость нужно настраивать с учётом конкретной службы; зоны не заменяют восстановление после отказа целого региона.
10. Область действия (scope) для Azure RBAC и Azure Policy — группа управления, подписка, группа ресурсов или ресурс. Назначения наследуются вниз. Платёжные области и роли каталога Entra относятся к другим системам полномочий.

## 2. Удостоверения и доступ \{#identity-and-access}

| Механизм | Что запомнить |
|---|---|
| Пользователь и группа | Пользователи представляют людей. Назначай доступ через группы и поддерживай актуальный состав участников. |
| [Регистрация приложения (app registration)](https://learn.microsoft.com/ru-ru/entra/identity-platform/app-objects-and-service-principals) | Задаёт глобальное описание (шаблон) приложения: идентификатор клиента, параметры входа, предоставляемые API и запрашиваемые разрешения. |
| [Субъект-служба (service principal)](https://learn.microsoft.com/ru-ru/entra/identity-platform/app-objects-and-service-principals) | Представляет приложение в конкретном тенанте; доступ выдаётся этому субъекту. У одного приложения может быть отдельный субъект-служба в каждом тенанте, где его используют. |
| [Управляемое удостоверение (managed identity)](https://learn.microsoft.com/ru-ru/entra/identity/managed-identities-azure-resources/overview) | Особый субъект-служба, чьими учётными данными управляет Azure. Подключённая рабочая нагрузка получает токены Entra без хранения паролей и ключей. |
| Назначаемое системой и назначаемое пользователем | Удостоверение, назначаемое системой (system-assigned), связано с одним ресурсом и удаляется вместе с ним. Назначаемое пользователем (user-assigned) — самостоятельный ресурс: его можно подключить к нескольким рабочим нагрузкам и сохранить при их замене. |
| [Azure RBAC](https://learn.microsoft.com/ru-ru/azure/role-based-access-control/overview) | Назначение доступа = субъект безопасности + определение роли + область действия. Роль задаёт разрешённые операции. Унаследованные разрешения сохраняются: роль Reader на более узкой области не отменит назначенную выше роль Contributor. |
| [Доступ к управлению и к данным](https://learn.microsoft.com/ru-ru/azure/storage/blobs/authorize-data-operations-portal) | Owner управляет ресурсами и доступом; Contributor — ресурсами, но не назначениями ролей; Reader позволяет просматривать конфигурацию. Для чтения данных обычно нужна отдельная роль, например Storage Blob Data Reader или Key Vault Secrets User. При этом полномочия на управление могут дать косвенный доступ к данным или возможность выдать такой доступ. |
| [Федерация удостоверений рабочей нагрузки (workload identity federation)](https://learn.microsoft.com/ru-ru/azure/developer/github/connect-from-azure-openid-connect) | GitHub Actions получает краткоживущий OIDC-токен. Entra проверяет issuer, subject и audience по федеративным учётным данным приложения или управляемого удостоверения, назначаемого пользователем, и выдаёт токен доступа к Azure. Нужны `id-token: write`, роли RBAC с минимальной областью действия и доверенная ветка или среда. Хранить секрет клиента не требуется. |
| [Conditional Access (условный доступ)](https://learn.microsoft.com/ru-ru/entra/identity/conditional-access/overview) | Политики доступа на основе удостоверений оценивают сигналы, например сведения о пользователе, устройстве, местоположении и риске, и применяют меры, например требуют MFA или блокируют доступ. |
| [Доступ из SDK без ключей (keyless access)](https://learn.microsoft.com/ru-ru/dotnet/api/azure.identity.defaultazurecredential?view=azure-dotnet) | `DefaultAzureCredential` проверяет настроенные источники учётных данных: например, локальную авторизацию разработчика или управляемое удостоверение в Azure, если оно настроено. Передай объект учётных данных клиенту SDK. Для прода явно выбери и ограничь источник учётных данных — часто подходит `ManagedIdentityCredential`; выдай роль на данные целевой службы. |

Проверяй три условия по отдельности: приложение может подключиться к конечной точке, получает подходящий токен и имеет право выполнить нужную операцию.

## 3. Сети \{#networking}

| Механизм | Назначение и границы |
|---|---|
| [VNet и подсеть](https://learn.microsoft.com/ru-ru/azure/security/fundamentals/network-overview) | VNet изолирует частное адресное пространство и маршруты. Подсети делят это адресное пространство для размещения рабочих нагрузок, интеграции служб и применения сетевых ограничений. |
| Группа безопасности сети (NSG) | Разрешает или запрещает передачу пакетов на подсети или сетевом интерфейсе по адресу, порту и протоколу; учитывает состояние соединений. Используй для ограничения связей между уровнями приложения. |
| [Частная конечная точка (private endpoint)](https://learn.microsoft.com/ru-ru/azure/virtual-network/vnet-integration-for-azure-services) | Сетевой интерфейс с частным IP-адресом в твоей VNet открывает доступ к поддерживаемой службе через Azure Private Link. Публичный доступ настраивается отдельно: сама конечная точка ещё не обеспечивает полную сетевую изоляцию. |
| [Конечная точка службы (service endpoint)](https://learn.microsoft.com/ru-ru/azure/virtual-network/vnet-integration-for-azure-services) | Служба распознаёт разрешённую подсеть; соединение идёт к публичной конечной точке по магистральной сети Azure. Частный IP-адрес службе не назначается. |
| Частная зона DNS (private DNS zone) | Обеспечивает разрешение имён в связанных VNet: обычные имена служб разрешаются в адреса частных конечных точек. Для собственного DNS и локальной инфраструктуры настрой перенаправление DNS-запросов. |
| [Интеграция PaaS с VNet](https://learn.microsoft.com/ru-ru/azure/app-service/overview-vnet-integration) | Позволяет приложению направлять исходящие соединения через VNet к частным зависимостям. В App Service для входящих частных соединений нужна отдельная частная конечная точка. |
| [Hub-and-spoke и Azure Firewall](https://learn.microsoft.com/ru-ru/azure/architecture/networking/architecture/hub-spoke) | В центральной VNet размещают общие сетевые подключения, DNS и средства проверки трафика; рабочие нагрузки — в отдельных VNet. Azure Firewall централизованно фильтрует и журналирует направленный через него трафик. [Пиринг VNet нетранзитивен](https://learn.microsoft.com/ru-ru/azure/virtual-network/virtual-networks-faq): маршруты между периферийными сетями и через средства проверки нужно задавать явно. |
| [Application Gateway + WAF](https://learn.microsoft.com/ru-ru/azure/networking/design-guide/app-delivery) | Региональный обратный прокси для HTTP(S): завершение TLS, маршрутизация по имени узла и пути, WAF рядом с региональными серверными компонентами. |
| [Azure Front Door + WAF](https://learn.microsoft.com/ru-ru/azure/networking/design-guide/app-delivery) | Глобальная пограничная служба HTTP(S): выбирает работоспособные региональные серверные компоненты, ускоряет доставку, кэширует ответы и применяет WAF. |
| [Azure Load Balancer](https://learn.microsoft.com/ru-ru/azure/networking/design-guide/app-delivery) | Распределяет соединения TCP и UDP по результатам проверок работоспособности. Работает на транспортном уровне: маршрутизации по HTTP-пути и WAF нет. |

При соответствующей настройке — до нуля. Kubernetes API не предоставляется. | Нужен контроль над кластером. Если холодный запуск нарушает требования к задержке, оставь минимальное число реплик. |

Отдельно оцени долгие HTTP-запросы и холодные запуски. |

Поды и узлы масштабируются отдельно. | Небольшому API или обработчику достаточно управляемого размещения, а обязанности по эксплуатации кластера избыточны. |
| [Virtual Machines (VMs)](https://learn.microsoft.com/ru-ru/azure/architecture/guide/technology-choices/compute-decision-tree) | Зависимости от конкретной ОС, устаревшее ПО или полный контроль над машиной. | ОС и ПО обслуживаешь ты. VM Scale Sets добавляют и удаляют машины. | Управляемая среда выполнения или база данных решает задачу и снимает работу по установке исправлений. |

## 5. Хранение данных \{#data}

| Служба | Что хранить и как выбирать |
|---|---|
| [Blob Storage](https://learn.microsoft.com/ru-ru/azure/storage/blobs/access-tiers-overview) | Объекты: файлы, документы, промежуточные результаты загрузки данных. Hot, Cool и Cold предлагают разное соотношение платы за хранение и обращения. Archive — автономный уровень: перед чтением данные нужно вернуть в оперативно доступное состояние. Уровень [Smart](https://learn.microsoft.com/ru-ru/azure/storage/blobs/access-tiers-smart) общедоступен (GA) в регионах публичного облака с зональной избыточностью. Он поддерживает блочные BLOB-объекты в учётных записях Standard GPv2 с ZRS, GZRS или RA-GZRS: после 30 дней без обращений объект переходит из Hot в Cool, после 90 дней — в Cold. Обращение возвращает объект в Hot. |
| [Azure SQL Database](https://learn.microsoft.com/ru-ru/azure/azure-sql/database/sql-database-paas-overview?view=azuresql) | Управляемый движок SQL Server: реляционные данные, транзакции, соединения таблиц и T-SQL. Microsoft обслуживает инфраструктуру, устанавливает исправления и делает резервные копии; схема и запросы остаются твоей задачей. |
| [Azure Database for PostgreSQL flexible server](https://learn.microsoft.com/ru-ru/azure/postgresql/extensions/how-to-use-pgvector) | SQL, экосистема PostgreSQL и pgvector, когда эмбеддинги нужны рядом с реляционными данными. Разреши расширение `vector` в списке допустимых, затем выполни `CREATE EXTENSION vector`. |
| [Azure Cosmos DB for NoSQL](https://learn.microsoft.com/ru-ru/azure/cosmos-db/request-units) | Документные данные с распределённым масштабированием. Ключ секционирования определяет распределение данных; единицы запросов (RU) — стоимость операций. Выбирай выделенную пропускную способность в RU/s или подходящий режим оплаты по потреблению. [Векторный индекс](https://learn.microsoft.com/ru-ru/azure/cosmos-db/vector-search) может храниться рядом с документами. |
| [Azure Managed Redis](https://learn.microsoft.com/ru-ru/azure/redis/overview) | Управляемый кэш в памяти: кэширование, сеансы, доступ с малой задержкой. Задай TTL, правила вытеснения и инвалидации: актуальность данных автоматически не обеспечивается. |

[Уровни согласованности Cosmos DB](https://learn.microsoft.com/ru-ru/azure/cosmos-db/consistency-levels), от самого строгого к самому слабому:

1. **Strong** — чтение возвращает последние зафиксированные данные.
2. **Bounded staleness** — отставание ограничено заданными пределами.
3. **Session** — гарантии в рамках сеанса, в том числе чтение собственных записей.
4. **Consistent prefix** — записи видны по порядку, без пропусков.
5. **Eventual** — реплики со временем сходятся; гарантий свежести и порядка нет.

Более строгие гарантии требуют компромиссов по задержке, доступности и пропускной способности.

## 6. Обмен сообщениями: Service Bus, Event Grid, Event Hubs \{#messaging}

| Служба | Модель | Типичная задача | Что учесть |

| [Service Bus](https://learn.microsoft.com/ru-ru/azure/service-bus-messaging/compare-messaging-services) | Брокер с очередями и подписками на темы; потребитель подтверждает обработку сообщения. | Команды и рабочие процессы, где нужно отследить завершение и отправить необработанное сообщение в очередь недоставленных сообщений. В Basic нет [транзакций](https://learn.microsoft.com/ru-ru/azure/service-bus-messaging/service-bus-transactions) и [сеансов](https://learn.microsoft.com/ru-ru/azure/service-bus-messaging/message-sessions); Standard и Premium поддерживают оба механизма. Сеансы позволяют сохранить порядок. | Учитывай повторную доставку: [обнаружение дубликатов](https://learn.microsoft.com/ru-ru/azure/architecture/guide/technology-choices/messaging) не гарантирует однократное выполнение внешних побочных эффектов. |
| [Event Grid](https://learn.microsoft.com/ru-ru/azure/service-bus-messaging/compare-messaging-services) | Отдельные события доставляются заинтересованным подписчикам. | Уведомление «создан BLOB-объект» без жёсткой связи между издателем и обработчиком. | Возможны дубликаты; общей гарантии порядка нет. |
| [Event Hubs](https://learn.microsoft.com/ru-ru/azure/service-bus-messaging/compare-messaging-services) | Секционированный журнал с добавлением в конец; группы потребителей независимо хранят свои позиции. | Телеметрия и потоки большого объёма для последующего анализа. | Сохранённые события можно читать повторно; порядок гарантируется внутри секции. Контрольные точки и идемпотентность обеспечивают потребители. |

Выбирай по задаче: выполнить работу с подтверждением, уведомить о факте или принять поток для анализа.

## 7. Секреты и конфигурация \{#secrets-and-config}

- [Key Vault](https://learn.microsoft.com/ru-ru/azure/key-vault/general/apps-api-keys-secrets): хранит секретные значения, выполняет криптографические операции с ключами и управляет жизненным циклом сертификатов. Используй [модель разрешений Azure RBAC](https://learn.microsoft.com/ru-ru/azure/key-vault/general/rbac-guide) с минимально необходимыми правами и разделением доступа к управлению и данным вместо прежних политик доступа.
- [App Configuration](https://learn.microsoft.com/ru-ru/azure/azure-app-configuration/overview): централизованные пары «ключ — значение» и флаги функций позволяют менять конфигурацию отдельно от сборки приложения. Секреты остаются в Key Vault, при необходимости — со ссылками из App Configuration.
- Доступ приложения: включи управляемое удостоверение; по мере необходимости выдай роли Key Vault Secrets User и [App Configuration Data Reader](https://learn.microsoft.com/ru-ru/azure/azure-app-configuration/concept-enable-rbac). Используй клиенты и поставщики конфигурации с аутентификацией по токенам. Выданные разрешения сами по себе не создают сетевой маршрут.

## 8. Инфраструктура как код и доставка изменений \{#infrastructure-and-delivery}

| Инструмент или механизм | Что делает |

## 9. Наблюдаемость \{#observability}

- [Azure Monitor](https://learn.microsoft.com/ru-ru/azure/azure-monitor/fundamentals/overview) собирает телеметрию инфраструктуры и приложений и позволяет реагировать на неё. Метрики и журналы служат основой панелей и оповещений.
- Рабочая область Log Analytics (Log Analytics workspace) хранит таблицы журналов и трейсов и управляет доступом к запросам. Application Insights показывает производительность приложения, зависимости и сбои, поддерживает распределённый трейсинг (tracing).
- OpenTelemetry даёт независимые от системы хранения средства инструментирования: трейсы (traces), метрики и журналы. [Текущие рекомендации для .NET, Node.js и Python](https://learn.microsoft.com/ru-ru/azure/azure-monitor/app/opentelemetry-enable) — Microsoft OpenTelemetry Distro; существующие интеграции с Azure Monitor OpenTelemetry Distro можно сохранить. Для Java используется Azure Monitor OpenTelemetry Distro. Экспортируй телеметрию в Azure Monitor и связывай запросы приложения, вызовы модели и спаны (spans) поиска.
- KQL (Kusto Query Language) обрабатывает таблицы цепочками фильтрации и агрегации. Ниже используются имена таблиц рабочей области [AppRequests](https://learn.microsoft.com/ru-ru/azure/azure-monitor/reference/tables/apprequests) и [AppExceptions](https://learn.microsoft.com/ru-ru/azure/azure-monitor/reference/tables/appexceptions); предполагается, что телеметрия уже поступает. Запросы сверены с документированными схемами, но не выполнялись в действующей среде Azure. Счётчики отражают число сохранённых записей; [p95 — оценка](https://learn.microsoft.com/ru-ru/kusto/query/percentiles-aggregation-function?view=azure-data-explorer) по этим записям. Выборка телеметрии может менять и итоговое количество, и наблюдаемое распределение задержек.

Записи о неуспешных запросах за последний час, по пятиминутным интервалам:

```kusto
// Failed request records during the last hour
AppRequests | where TimeGenerated > ago(1h) and Success == false
| summarize Failures=count() by bin(TimeGenerated, 5m)
```

Пять конечных точек с наибольшим p95 длительности запроса в миллисекундах за последний час:

```kusto
// Slow endpoints: p95 duration in milliseconds
AppRequests | where TimeGenerated > ago(1h)
| summarize P95=percentile(DurationMs, 95) by Name | top 5 by P95 desc
```

Пять самых частых групп исключений за последний час:

```kusto
// Most frequent exception groups
AppExceptions | where TimeGenerated > ago(1h)
| summarize Records=count() by ProblemId | top 5 by Records desc
```

## 11. AI в Azure \{#ai-on-azure}

Базовые методы разобраны в уроках о [поиске (retrieval)](/rag-agents/part-1-rag/retrieval/), [использовании инструментов (tool use)](/rag-agents/part-2-agents/tool-use/) и [оценке (evaluation)](/rag-agents/part-1-rag/cross-cutting/evaluation/).

[Microsoft Foundry](https://learn.microsoft.com/ru-ru/azure/foundry/what-is-foundry) — текущее название платформы, ранее Azure AI Foundry. [Ресурс Foundry](https://learn.microsoft.com/ru-ru/azure/foundry/concepts/architecture) объединяет сетевые настройки, безопасность и развёртывания моделей. Внутри него проекты содержат агентов, оценки и материалы разработки. У подключённых Search, Storage и Key Vault сохраняются собственные границы доступа и сетевые настройки. Прежние проекты на основе хаба (hub-based) относятся к классическому интерфейсу (classic experience).

[Развёртывание модели (model deployment)](https://learn.microsoft.com/ru-ru/azure/foundry-classic/openai/how-to/create-resource) — именованная конечная точка для одной версии модели с выбранными типом развёртывания и мощностью. В коде указывается имя развёртывания. Azure OpenAI в Microsoft Foundry Models предоставляет модели OpenAI; в каталоге есть и другие поставщики. Для каждой модели отдельно проверяй API, варианты развёртывания и условия использования: одинаковое поведение не гарантируется.

Ниже — основные типы онлайн-развёртываний [Serverless API](https://learn.microsoft.com/ru-ru/azure/foundry/concepts/deployments-overview). Размещение на управляемых вычислительных ресурсах (managed compute) устроено иначе. [Границы обработки и тарификация](https://learn.microsoft.com/ru-ru/azure/foundry/foundry-models/concepts/deployment-types) зависят от типа развёртывания.

## 13. Power Platform в шести пунктах \{#power-platform}

1. [Power Apps](https://learn.microsoft.com/ru-ru/power-platform/developer/get-started) — интерфейсы low-code приложений поверх подключённых данных. Собственные API и компоненты расширяют возможности визуального конструктора.
2. [Power Automate](https://learn.microsoft.com/ru-ru/power-platform/developer/get-started) — облачные и настольные потоки, автоматизирующие работу через соединители: по событию, расписанию или действию пользователя.
3. [Dataverse](https://learn.microsoft.com/ru-ru/power-apps/maker/data-platform/data-platform-intro) — управляемая платформа бизнес-данных: таблицы, связи, безопасность и API. Приложения платформы могут работать с общими данными.
4. [Copilot Studio](https://learn.microsoft.com/ru-ru/power-platform/developer/get-started) — графический low-code конструктор агентов и потоков агентов; подключает знания и инструменты к диалоговым приложениям.
5. [Пользовательские соединители (custom connectors)](https://learn.microsoft.com/ru-ru/connectors/custom-connectors/) оборачивают REST API в повторно используемые действия и триггеры для Power Apps, Power Automate и Copilot Studio. Серверной частью может быть API на ASP.NET Core.
6. Собственный код: размести логику за API с аутентификацией и предоставь доступ через соединитель. Сохраняй явные права на данные и дисциплину развёртывания. Тестируй API вместе с соединителем, включая отказы в авторизации.

## 14. Десять вопросов для самопроверки \{#review-questions}

После курса ты должен уметь ответить на эти вопросы и объяснить выбор механизмов в каждом ответе.

| Вопрос | Что должно быть в ответе |
|---|---|
| 1. Как организовать ресурсы Azure? | Тенант и группы управления для общих правил и ограничений; подписки для раздельного администрирования рабочих нагрузок, сред и расходов; группы ресурсов по жизненному циклу. Осознанный выбор областей действия для минимальных прав и Policy. |
| 2. Почему при роли Contributor доступ всё равно запрещён? | Различие между правами плоскости управления и доступом к данным службы. Кто вызывает службу, для какого получателя выдан токен, есть ли роль на данные в нужной области и сетевое подключение. |
| 3. Как закрыть RAG-систему от публичного доступа? | Исходящее подключение приложения к VNet; частные конечные точки и DNS для моделей, Search и секретов; при необходимости отключение публичного доступа; управляемое удостоверение и роли на данные. Также опиши, как задания загрузки документов, операторы и CI получают доступ к этим ресурсам. |
| 4. Container Apps, App Service, Functions или AKS? | Модель запросов и триггеров, потребность в контейнерах, задержки и обязанности по эксплуатации. Управляемое размещение приложения, если контроль Kubernetes не требуется. Проверка масштабирования и холодного запуска относительно SLO. |
| 5. Как восстановиться после отказа региона? | Целевое время восстановления и допустимая потеря данных; мощности приложения в регионах, репликация, резервные копии и маршрутизация. Зоны защищают только от отказов внутри региона. Проверки переключения, восстановления и доступности зависимостей. |
| 6. Какая служба сообщений подходит для загрузки данных? | Event Grid сообщает о новых материалах; Service Bus ставит работу в очередь до завершения; Event Hubs принимает потоки с порядком внутри секций. Повторы, сообщения, вызывающие постоянную ошибку, и идемпотентность на границах приложения. |
| 7. Как выбрать хранилища для RAG? | Blob для оригиналов, SQL или PostgreSQL для реляционного состояния, Search для управляемого гибридного поиска, Cosmos для секционированных документов, Redis для кэша. Выбор по характеру запросов и обновлений и измеренному качеству поиска; одной поддержки векторов недостаточно. |
| 8. Global Standard или Provisioned для модели? | Сначала ограничения на место обработки данных, затем измерения состава токенов, параллелизма и задержек. Сравни гибкость оплаты за токены с загрузкой зарезервированных PTU. Проверка предположений о квотах, мощностях и переключении при отказе. |
| 9. Как безопасно выпускать изменения и искать ошибки? | Версии IaC и образов, OIDC в CI, проверки до переключения запросов на слот или ревизию. Связывай трейсы запроса, поиска и модели. Проверяй качество поиска и ответов воспроизводимыми оценками; блокируй выпуск, если проверка не пройдена, и сохраняй возможность отката. |
| 10. Как контролировать затраты и безопасность? | Policy для требований к конфигурации, RBAC для ограничения доступа, Defender for Cloud для выявления рисков. Теги владельца и среды, анализ расходов и бюджетные оповещения. Ограничения токенов и параллелизма: бюджеты не ограничивают потребление. |
